## 밟으면 아픈 곳 ★

작업 중 실제로 밟았거나, 밟기 쉬운 지점들이다.

### 1. Eloquent dirty 체크 — 스테일 모델

`$model->update([...])` 는 **변경된 속성만** SQL 로 보낸다. 모델을 미리 로드해둔 사이에 다른 코드가 DB 를 바꿨다면, 메모리 값과 넘긴 값이 같아서 **쿼리가 아예 나가지 않는다.**

배송비 정책 테스트 정리 중 이걸로 기본 정책이 0개가 되는 상태를 만들었다. 강제로 써야 할 때:

```php
$model->refresh();                     // 또는
$model->forceFill([...])->save();      // dirty 체크 우회
```

### 2. 라이브러리를 우회하면 불변식이 깨진다

`ShippingPolicyLibrary` 는 "활성 기본 정책 정확히 1개"를 지키지만, `$policy->delete()` 처럼 **모델을 직접 만지면 그 보호가 없다.** 시더·커맨드·테스트에서도 라이브러리를 거치는 편이 안전하다.

기본 정책이 0개가 되면 `defaultPolicy()` 가 예외를 던진다. **의도된 동작이다** — 조용히 0원 처리하면 주문 금액이 틀린 채로 쌓인다.

### 3. Str::slug 는 한글을 전부 버린다

`Str::slug('의류')` → `''`. 그대로 두면 모든 한글 카테고리가 `category-2`, `category-3` 이 된다.
`CategoryLibrary::resolveSlug()` 에 한글 보존 폴백을 넣어뒀다. **상품 slug 를 만들 때 같은 처리가 필요하다.**

### 4. DB::raw 를 무심코 쓰게 된다

카테고리 depth 재계산에 `DB::raw('depth + N')` 을 썼다가 CLAUDE.md §5.1 위반이라 `increment()`/`decrement()` 로 고쳤다. 이식성 규칙은 **쓰는 순간에는 잘 안 떠오른다.** 커밋 전에 `grep -rn "DB::raw\|whereRaw\|selectRaw" app/` 한 번.

### 5. 관리자 라우트 이름에 admin. 을 또 붙이면 admin.admin.

`bootstrap/app.php` 의 `->name('admin.')` 이 자동으로 붙는다. `routes/admin.php` 안에서는 `admin.` 없이 쓴다.

### 6. PowerShell 로 php artisan tinker --execute 는 이스케이프가 깨진다

`$` 와 `\` 때문에 파스 에러가 난다. **스크립트 파일로 만들어** `php artisan tinker path/to/script.php` 로 실행할 것.

### 7. Bash 툴의 작업 디렉터리는 유지되지만 리셋되기도 한다

`cd shop && ...` 없이 상대경로로 `CLAUDE.md` 를 열면 상위 폴더에 엉뚱한 파일이 생긴다. 실제로 한 번 발생했다. **절대경로를 쓸 것.**

### 8. 컬럼을 추가하면 모델 Fillable 에도 넣어야 한다

마이그레이션에 `orders.payment_due_at` 을 넣고 `create([...'payment_due_at' => $due])` 를 했는데,
모델 `#[Fillable]` 에 없어서 **조용히 누락됐다.** 예외도 경고도 없다.

그 결과 `expireStaleOrders()` 의 `whereNotNull('payment_due_at')` 에 걸리지 않아
**해당 주문들이 영원히 만료되지 않는 상태**가 됐다. 화면의 '입금기한 -' 을 보고 발견했다.

컬럼 추가 시 같이 볼 것: `Fillable`, `casts`.
전수 점검 스크립트를 한 번 돌려볼 만하다 (`Schema::getColumnListing` vs `getFillable`).

### 9. 옵션을 지운 뒤에 조합 이름을 만들면 틀어진다

`syncOptions` 가 빠진 옵션 값을 지우면 `product_variant_values` 가 cascade 로 끊긴다.
그 뒤에 조합 이름을 계산하면 `빨강 / S` 가 `S` 로 나온다. **조합 매칭과 오류 메시지가 둘 다 틀어진다.**

`ProductLibrary::syncOptionsAndVariants()` 는 옵션을 손대기 **전에** 조합 이름을 찍어두고 그것으로 매칭한다. 실제로 이 버그를 만들었다가 고쳤다.

### 10. SKU 는 저장할 때마다 바뀌면 안 된다

`resolveSku()` 가 빈 값을 받으면 새로 만들도록 짰더니, 수정 저장 때마다 SKU 가 갈렸다.
SKU 는 재고·물류 식별자라 바깥 시스템과 어긋난다. **기존 조합이면 있던 SKU 를 지킨다.**

### 11. reserved_quantity 는 폼에서 절대 덮어쓰지 않는다

시스템(주문/결제)이 관리하는 값이다. 상품 수정 폼은 `stock_quantity` 만 보낸다.
대신 **실물을 예약분보다 적게 줄이는 것은 막는다** — 판매가능이 음수가 되기 때문이다.

### 12. SQLite 에서 검증할 수 없는 것

- `lockForUpdate()` 무효 → **재고 동시성은 로컬 테스트로 안전을 보장할 수 없다** (§7.6)
- `LIKE` 대소문자 구분 안 함 → 검색은 PostgreSQL 에서 다르게 동작한다

### 13. 사용 처리를 먼저 하면 할인액이 0 이 된다 (실제로 터졌던 버그)

`OrderLibrary::createFromCart()` 는 이렇게 되어 있었다.

```php
$userCoupon = $this->coupons->markUsed($userCouponId, $userId);  // used_at 을 찍는다
$discount   = $this->coupons->discountFor($userCoupon, $itemsTotal);
```

`discountFor()` 안에 `! $userCoupon->isUsable()` 검사가 있었고, `isUsable()` 은
`used_at` 이 비어 있는지를 본다. 방금 자기가 찍은 `used_at` 때문에 **항상 0** 이
나왔고, 바로 아래 `if ($discount <= 0) throw` 에 걸려
**쿠폰을 선택한 주문이 전부 "이 주문에 사용할 수 없는 쿠폰입니다" 로 막혔다.**

쿠폰 라이브러리 단위 테스트(`coupontest.php`)는 전부 통과했다 —
`markUsed()` 와 `discountFor()` 를 따로 불렀기 때문이다.
**실제 주문 경로로 한 번도 안 태워봤던 것**이고, 반품 쿠폰 안분을 검증하려고
쿠폰 붙은 주문을 만들다가 그제야 드러났다.

`discountFor()` 에서 `used_at` 검사를 뺐다. 사용 가능 여부는 `markUsed()` 와
`usableFor()` 가 판단하고, `discountFor()` 는 계산만 한다. 만료·비활성 검사는 남겼다.

교훈: **라이브러리 단위로 통과했다고 그 기능이 동작하는 게 아니다.**
호출 순서까지 포함한 실제 경로로 한 번은 태워봐야 한다.

### 14. 반품에서 조합 표시명을 다시 만들지 말 것

`product_variants` 에는 이름 컬럼이 없다. 표시명은 `optionValues` 를
옵션 `sort_order` 로 정렬해 `' / '` 로 이어 만든다 (`CartLibrary` 와 같은 규칙).
`ReturnLibrary::variantLabel()` 이 그 규칙을 따른다.

단, **주문 항목에 이미 찍힌 `variant_name` 이 있으면 그쪽이 우선이다** —
주문 당시 이름이 스냅샷이고, 옵션값이 바뀌어도 변하면 안 된다 (§4.3).
`variantLabel()` 은 '앞으로 보낼 교환품' 처럼 스냅샷이 없는 경우에만 쓴다.

### 15. 부분 반품에서 쿠폰 할인은 매번 따로 내림하면 안 된다

75,000원 주문에 7,000원 쿠폰, 1개(25,000) → 2개(50,000) 로 나눠 반품하면
매 건 따로 `floor(7000 × 25000/75000)` = 2,333 씩 계산해 합이 6,999 가 된다.
**잔돈 1원이 영원히 안 돌아간다.**

`calculateAmounts()` 는 **누적 기준**으로 계산한다.
`floor(할인 × (이전누계 + 이번)/상품합계) − 이미차감액` → 마지막 건이 잔돈을 흡수한다.
검증에서 2,333 + 4,667 = 7,000, 환불 합계 = 결제액 68,000 으로 정확히 맞았다.

### 16. 관리자 메뉴를 추가하면 기존 역할에 권한이 없다

`config/admin/menu.php` 에 `STAT_SALES` 를 넣었는데 사이드바에 '통계' 가 안 떴다.
권한의 원천은 config 지만 **판단은 DB(`admin_role_permissions`)** 가 하고,
없는 레코드는 차단이 기본값이기 때문이다 (CLAUDE.md §7.2).

`SUPER_ADMIN` 은 하드코딩 예외라 멀쩡히 보여서 더 헷갈린다 —
최고관리자로만 확인하면 못 잡는다. **권한 제한된 계정(`manager1`)으로 확인할 것.**

메뉴를 추가하면 같이 할 일:
- 시드를 다시 돌리거나 (`shop:demo --fresh`)
- 관리자 > 설정 > 권한설정에서 역할별로 체크

운영 중이라면 시드를 못 돌리므로 **권한설정 화면에서 직접 켜야 한다.**

### 17. 대시보드는 라우트 미들웨어 하나로 못 막는다

여러 메뉴의 숫자를 한 화면에 모으므로 `admin.permission:X` 하나로는 못 거른다.
사이드바에서 '매출' 메뉴를 숨겨놓고 대시보드에 매출을 찍으면 권한 분리가 무의미해진다.

`DashboardLibrary` 는 **카드마다 `menu_code` 를 달고** `allows()` 로 걸러
권한 없는 블록은 아예 `null` 로 내린다. 화면은 `v-if` 로 안 그린다.
검증도 화면이 아니라 **라이브러리 반환값**으로 했다 (`PRODUCT_LIST` 만 가진 계정 →
`sales/series/recent_orders/members` 전부 null, 처리대기 카드 0개).

### 18. SKU 를 상품 slug 로 만들면 한글에서 무너진다 (실제로 터졌던 버그)

`resolveSku()` 가 `Str::upper(Str::slug($product->slug))` 로 base 를 만들었다.
**한글 slug 는 `Str::slug` 가 전부 버려서 빈 문자열이 된다**(§3 과 같은 함정).
그래서 base 가 항상 `'SKU'` 로 떨어졌다.

옵션이 있는 상품은 랜덤 4자리가 붙어 가려졌지만, **옵션 없는 상품은 랜덤도 안 붙어서**
`SKU`, `SKU-2` 로 생성되고 있었다. 충돌 회피 접미사만 다른 셈이라 식별자 구실을 못 한다.

바로구매 검증 중 재고 부족 메시지가 `(SKU SKU: 23개 남음)` 으로 찍혀서 발견했다.

지금은 `P{상품id}-{랜덤4}` 다. 상품 id 는 항상 ASCII 이고 바뀌지 않으며,
**옵션이 없어도 랜덤을 붙인다.** 기존 조합의 SKU 는 그대로 지킨다(§10).

교훈: **`Str::slug` 를 쓰는 자리는 전부 한글을 넣어봐야 한다.**
카테고리에서 한 번 밟고도 상품 SKU 에서 또 밟았다.

### 19. 평점을 평균으로 저장하면 되돌릴 수 없다

`products` 에 `rating_avg` 하나만 두면 후기가 숨겨질 때 **원래대로 못 돌린다.**
평균만으로는 "이 후기가 몇 점이었나" 를 복원할 수 없고, 부동소수라 누적 오차도 쌓인다.

`rating_sum`(정수 합) + `review_count`(건수)로 두면 가감이 정확하다.
평균은 화면에 그릴 때 나눈다.

그리고 **상태 변경은 멱등해야 한다.** 숨김을 두 번 누르면 평점이 두 번 빠진다 —
재고 예약 해제와 똑같은 함정이다 (schema-draft.md §7.4).
`setStatus()` 는 같은 상태면 아무것도 하지 않는다.

### 20. 비밀글은 화면에서 가리면 안 된다

`v-if` 로 안 그리는 건 가린 게 아니다. Inertia props 는 HTML 안에 그대로 들어가 있어
개발자도구로 다 보인다. **서버가 내용을 `null` 로 만들어 내려야 한다.**

`ProductQuestion::isVisibleTo()` 가 판단하고 `ProductQuestionLibrary::present()` 가
`content`·`answer` 를 지운다. 목록에서 행 자체를 빼지는 않았다 —
아예 없애면 '답변대기 2건' 같은 숫자가 화면과 안 맞는다.

### 21. 시더가 데이터를 다 채우면 기능을 볼 수 없다

배송완료 주문 **전부**에 후기를 달았더니 '후기 쓰기' 화면과 상품 상세의 작성 폼이
영원히 빈 채로 나왔다. 만들어둔 기능을 확인할 방법이 없어진다.

`DemoReviewSeeder` 는 마지막 항목 하나를 일부러 비워둔다.
**데모 데이터는 "가득 찬 상태" 가 아니라 "만져볼 수 있는 상태" 여야 한다.**

### 22. User::create() 에 Fillable 밖 컬럼을 넣으면 조용히 사라진다

`CreateNewUser::create()` 에서 처음엔 이렇게 썼다:

```php
return User::create([
    'name' => ..., 'email' => ..., 'password' => ...,
    'marketing_email_agreed_at' => $agreed ? now() : null,  // Fillable 에 없다!
]);
```

`marketing_*_agreed_at` 은 **일부러** `User::$fillable` 에서 뺐다(법적 증빙 컬럼을
폼 mass assignment 로 못 건드리게 하려고, §18 과 같은 이유). 그런데 `create()` 자체가
mass assignment 라, 이 배열에 넣어도 **에러 없이 조용히 버려진다** — worklog #8 이
`orders.payment_due_at` 에서 이미 겪은 바로 그 함정이 이번엔 내 손으로 재현됐다.

고치기 전에 검증 스크립트로 먼저 잡았다: 가입 직후 `$user->marketing_email_agreed_at`
이 항상 null 이었다. `User::create()` 로 기본 필드만 만들고, 동의 시각은 별도로
`forceFill()->save()` 로 쓰는 걸로 갈랐다.

**교훈:** Fillable 을 일부러 좁혀둔 컬럼은, **그 모델을 처음 만드는 지점에서도**
`create()` 배열에 절대 섞지 않는다. 생성과 시스템 컬럼 설정을 항상 두 단계로 나눈다.

### 23. Fortify 의 상태 슬러그를 그대로 찍으면 화면에 영어가 뜬다

Fortify 내장 `ProfileInformationController` 는 저장 성공 시
`session('status', 'profile-information-updated')` 를 쓴다. 이 앱의 다른 모든 컨트롤러는
`->with('status', '완성된 한국어 문장')` 을 넣는 게 관례였는데, Fortify 만 예외다.

`StoreLayout` 은 `flash.status` 를 **전역 배너로 그대로 찍는** 구조라, "내 정보" 저장을
누르면 화면에 `profile-information-updated` 라는 원본 슬러그가 그대로 노출됐다 —
개별 페이지에서 슬러그를 번역해도 전역 배너가 먼저(또는 같이) 그려서 중복으로 보였다.

**고친 곳은 한 곳— `HandleInertiaRequests::translateStatus()`.** `flash.status` 를
공유 데이터로 내리는 자리에서 알려진 Fortify 슬러그만 한국어로 바꿔둔다.
페이지마다 `VerifyEmail.vue` 식으로 슬러그를 하드코딩해서 대응하면 다음 Fortify
라우트(비밀번호 변경 등)를 쓸 때마다 또 같은 실수를 반복한다.

**교훈:** 공유 레이어(Inertia shared data)를 통과하는 값은, 그 값이 프레임워크가
만든 것이든 앱이 만든 것이든 **같은 계약(완성된 한국어 문장)을 지켜야** 화면에서
안전하게 그대로 찍을 수 있다. 계약을 못 지키는 소스가 있으면 계약 진입점에서 맞춘다.

### 24. 리스너를 두 번 등록하면 두 번 실행된다

`RecordUserLogin` 리스너를 만들고 `AppServiceProvider::boot()` 에
`Event::listen(Login::class, RecordUserLogin::class)` 로 손수 등록했다.
그런데 이미 §7 노트(367번 줄)에 적혀 있던 대로 **Laravel 11+ 는 `app/Listeners`
안의 클래스를 `handle()` 타입힌트만 보고 자동 등록한다** — 기존
`MergeGuestCartOnLogin` 도 그래서 어디에도 명시적 등록이 없다.

`php artisan event:list` 로 확인하니 `RecordUserLogin@handle` 이 같은 이벤트에
**두 줄** 찍혀 있었다 — 로그인 한 번에 `forceFill(['last_login_at'=>now()])->save()`
가 두 번 실행되고 있었다는 뜻이다. 결과값 자체는 같아서(같은 시각으로 두 번 쓰기)
겉으로는 버그처럼 안 보였다 — `event:list` 로 등록 목록을 직접 안 봤으면
못 잡았을 것이다.

**교훈:** 이 프로젝트에서 새 리스너를 추가할 때 `Event::listen()` 을 직접 쓰지
않는다. `app/Listeners/` 에 클래스만 두면 된다. 추가한 뒤에는 항상
`php artisan event:list` 로 정확히 한 번만 등록됐는지 확인한다.

### 25. 브라우저 프리뷰가 Vite 개발서버가 아니라 빌드된 정적 자산을 서빙한다

간편로그인 버튼을 Vue 컴포넌트로 새로 만들고 `Login.vue`/`Register.vue` 에
연결한 뒤, 프리뷰 브라우저로 확인했는데 **버튼이 전혀 안 보였다.** 서버 쪽은
`socialLogin: {kakao:true, naver:true}` 를 정확히 내려주고 있었고(`curl` 로
직접 확인), 콘솔에도 에러가 없었고, 새 탭으로 열어도 새로고침을 해도 그대로였다.

`preview_logs` 로 실제 요청 로그를 보고서야 원인을 찾았다 — 요청이
`/build/assets/app-xxxxxxxx.js` 처럼 **해시가 붙은 프로덕션 빌드 파일**을
서빙하고 있었다. 이 프로젝트의 프리뷰 서버는 `npm run dev`(Vite HMR) 가 아니라
`php artisan serve` 가 `public/build` 의 **정적 빌드 산출물**을 그대로 내려주는
구성이었다 — 즉 Vue 파일을 고쳐도 `npm run build` 를 다시 돌리기 전까지는
브라우저에 반영되지 않는다.

**교훈:** 프런트엔드(.vue) 파일을 고친 뒤 브라우저로 검증하기 전에는
**항상 `npm run build` 부터 실행한다.** "서버 응답은 맞는데 화면에 안 보인다"
증상이 나오면 콘솔·네트워크보다 먼저 `preview_logs` 로 어떤 파일을 서빙
중인지(`/build/assets/...` 해시 vs Vite 개발서버 경로) 확인할 것.

### 26. 리다이렉트로 보낸 에러는 useForm 이 못 본다 — 화면에서 조용히 사라진다

간편로그인 실패 시 `redirect()->route('login')->withErrors(['email' => $msg])` 로
사유를 돌려보냈는데, **로그인 화면에 아무것도 안 떴다.** 서버는 에러를 정확히
넣어 보내고 있었다(리다이렉트도 정상). 그냥 화면이 안 그렸을 뿐이다.

원인: `Login.vue` 는 `form.errors.email` 을 보는데, **`useForm` 의 `errors` 는
그 폼이 직접 보낸 요청의 응답만 받는다.** 다른 라우트에서 리다이렉트로 넘어온
에러는 공유 프롭 `usePage().props.errors` 에만 들어간다 — 이 앱의 관리자 화면들이
전부 `usePage().props.errors.general` 을 직접 읽어 배너로 띄우는 이유가 이것이다
(`Admin/Order/Show.vue` 등 여러 곳에 같은 패턴이 이미 있었는데 못 보고 지나쳤다).

고친 방법: 컨트롤러는 `general` 키로 보내고, `Login.vue` 에 공유 errors 를 읽는
배너를 하나 뒀다. **이 버그는 원래 있던 OAuth 실패 처리에도 그대로 있었다** —
"간편로그인에 실패했습니다" 도 화면에 안 뜨고 있었다는 뜻이다.

**교훈:** 다른 라우트로 **리다이렉트하면서** 에러를 실을 때는, 받는 화면이
`form.errors` 가 아니라 `usePage().props.errors` 를 읽는지 반드시 확인한다.
같은 화면 안에서 `back()->withErrors()` 로 되돌리는 경우(폼 자신의 제출)는
`form.errors` 로 정상 동작하므로 헷갈리기 쉽다.

### 27. 화면 시간대는 저장 시간대를 바꿔서 고치면 안 된다

주문일시가 9시간 어긋나 보였다. DB 는 UTC 로 저장하는데(전 테이블 공통 규칙)
라이브러리가 `toDateTimeString()` 을 그대로 내보내고 있었다.

**`config('app.timezone')` 을 Asia/Seoul 로 바꾸는 게 제일 빠른 유혹이다.** 그러면
새로 쌓이는 값은 KST, 기존 값은 UTC 가 되어 **과거 데이터가 통째로 9시간 틀어진다.**
게다가 통계의 날짜 경계 계산(`StatLibrary`)이 이미 UTC 저장을 전제로 짜여 있어서
같이 무너진다.

저장은 UTC 그대로 두고 **내보낼 때만** 바꿨다(`App\Support\LocalTime`).
라이브러리가 배열로 내려주는 `*_at` 55곳을 전부 이걸로 통과시켰다.

**주문번호에도 날짜가 들어간다**(`ORD20260825...`)는 걸 놓칠 뻔했다. 이것도 UTC 라
한국 시간 오전 9시에 날짜가 바뀌어, 25일 저녁 주문이 26일자 번호를 달고 나왔다.

**교훈:** 시간대 문제는 "어디서 바꿀 것인가" 가 전부다. **저장 계층은 건드리지 않는다.**
표시용 변환은 한 군데(헬퍼)로 모으고, 날짜가 값에 섞여 들어가는 곳(주문번호 같은)이
없는지 따로 훑는다.

### 28. flex-1 / 그리드 칸은 min-w-0 없이는 줄어들지 않는다

좁은 화면에서 관리자 대시보드와 매출통계에 가로 스크롤이 생겼다. `truncate` 를
붙여놨는데도 상품명이 칸을 밀어냈다.

원인은 CSS 기본값이다. **flex 아이템과 그리드 아이템은 `min-width: auto`** 라서
내용의 min-content 아래로 줄어들지 않는다. `flex-1 truncate` 는 그래서 아무것도
자르지 못하고, `grid-cols-2` 칸은 안쪽 목록이 요구하는 만큼 넓어진다.

고친 곳:
- `flex-1 truncate` → `min-w-0 flex-1 truncate` (대시보드 인기상품·최근주문)
- 그리드 안의 `<section>` → `class="min-w-0"` (대시보드, 매출통계)
- 일별 그래프의 막대·라벨 `flex-1` → `min-w-0` (막대 30개면 통째로 밀어낸다)

**교훈:** 좁은 화면에서 가로 스크롤이 생기면 넘치는 요소만 보지 말고 **그 조상 중
flex/grid 컨테이너**를 찾는다. 대개 `min-w-0` 한 줄이 빠져 있다. 넘치는 요소를
찾는 데는 `getBoundingClientRect().right > clientWidth` 로 전부 훑는 스크립트가 빠르다.

### 29. 표를 overflow-x-auto 로 감쌀 때 v-if 를 같이 옮겨야 한다

표 19개를 스크롤 컨테이너로 감쌌더니 빌드가 깨졌다 —
`v-else/v-else-if has no adjacent v-if`.

`<table v-if="...">` 를 감싸면 래퍼 `<div>` 가 `v-if` 와 뒤따르던 `v-else` 사이에
끼어들어 둘이 더 이상 형제가 아니게 된다. `v-if` 를 래퍼로 올려서 해결했다.

**교훈:** 조건부 렌더링이 붙은 요소를 감쌀 때는 **조건을 래퍼로 올린다.** 일괄 치환
스크립트를 돌린 뒤에는 반드시 빌드를 돌려본다 — 이건 문법 오류라 빌드가 잡아준다.

### 30. Tailwind 4 는 버튼 커서를 `default` 로 되돌린다

버튼 124개 중 `cursor-pointer` 가 붙은 건 4개뿐이었다. 누를 수 있는 요소인지
손 모양으로 알 수 없는 상태였는데, 화면을 만들 때는 아무도 눈치채지 못했다.

원인은 우리 코드가 아니라 **Tailwind 4 의 Preflight 변경**이다. v3 는 `button` 에
`cursor: pointer` 를 줬지만 v4 는 브라우저 기본값(`default`)을 따른다.

**컴포넌트마다 클래스를 붙이는 방식으로 고치지 않았다.** 화면이 45개라 반드시
빠뜨리는 곳이 생긴다. `resources/css/app.css` 의 `@layer base` 에서 한 번에 정했다
(비활성 버튼은 제외 — 누를 수 없는데 손 모양이면 거짓말이다).

**교훈:** 메이저 버전을 올린 프레임워크는 **기본값이 바뀐 곳**을 의심한다.
우리가 쓴 적 없는 규칙이 사라져 있을 수 있고, 그건 코드를 아무리 봐도 안 보인다.

### 31. 외부 이미지를 시드에 쓰면 시딩이 네트워크에 묶인다

데모 상품 사진을 실사로 바꾸면서 **시드할 때 내려받는 방식을 쓰지 않았다.**
그러면 네트워크가 없거나, 원본 서비스가 URL 형식을 바꾸거나, 사진이 내려가면
`shop:demo` 가 통째로 실패한다 — 데이터를 채우는 일이 남의 서버에 묶인다.

받아서 저장소에 넣어두고, **파일이 없으면 예전 방식(GD)으로 물러나게** 했다.
사진을 지워도 시딩은 끝까지 돈다.

또 하나: **업로드에 원본 경로를 그대로 넘기면 안 된다.** 업로드 처리가 파일을
옮기거나 지우면 저장소의 원본이 사라져서, 다음 `--fresh` 부터 사진 없이 돌게 된다.
임시 파일로 복사해서 넘긴다.

**교훈:** 시드 데이터는 **오프라인에서 재현 가능해야 한다.** 외부 자원을 쓸 거면
받아서 저장소에 넣고, 없을 때의 폴백을 같이 만든다.

## 단계별 기록

### 2026-08-20 — 환경 구축

- PHP 8.4 / Composer 를 winget 으로 설치. **시스템에 다른 PHP 가 없고 `php.ini` 도 winget 패키지 폴더에만 있다** (CLAUDE.md §3.1). 확장을 켤 일이 생기면 그 파일을 고친다.
- PostgreSQL 18.6 설치, 서비스 자동 시작. **아직 프로젝트 DB(`shop`)는 안 만들었다** — 지금은 SQLite 로 개발 중이라 급하지 않다. 절차는 CLAUDE.md §5.4.
- `pdo_pgsql`/`pgsql` 확장은 이미 켜둬서 PostgreSQL 전환 시 PHP 쪽 추가 작업은 없다.

### 인증

- **Fortify 는 단일 가드다** (`config/fortify.php` 의 `'guard' => 'web'`). 그래서 관리자는 수동 구현이 강제됐다. 이게 이 프로젝트에서 Breeze/스타터킷을 안 쓴 실질적 이유다.
- Breeze 는 README 상 Laravel 11.x 이하용이라 후보에서 뺐다.
- 2FA·패스키는 껐고 마이그레이션도 지웠다. 켜려면 `config/fortify.php` 주석 해제 + `vendor:publish` 재실행 + 화면 제작.
- **로컬 메일은 `MAIL_MAILER=log`** — 인증 메일은 `storage/logs/laravel.log` 에서 확인한다.

### 관리자 권한

- **메뉴 정의의 원천은 `config/admin/menu.php`** 다. DB 는 "어떤 역할이 어떤 `menu_code` 에 접근 가능한가"만 저장한다. 메뉴를 추가해도 마이그레이션이 필요 없다.
- 사이드바는 `HandleInertiaRequests` 가 공유 데이터로 내린다. 컨트롤러마다 넘기지 않는다.
- **라우트가 없는 메뉴는 링크가 아니라 회색 텍스트**로 렌더된다 (`AdminMenuLibrary` 가 `Route::has()` 로 판단). 상품·주문 등이 지금 이 상태다.
- 시더의 운영자 권한은 `SETTING_` **접두사가 아니라** 막을 코드(`SETTING_ROLE`, `SETTING_ADMIN`)를 명시해 거른다. 배송비설정도 `SETTING_` 이지만 운영 업무라 접두사로 거르면 안 된다.

### 카테고리

- 계층 최대 3단계. `depth` 는 부모에서 파생되지만 트리 조회를 매번 재귀하지 않으려고 **비정규화**했다.
- **부모를 옮기면 자손 `depth` 를 통째로 밀어준다.** 이걸 빼면 트리가 조용히 어긋난다.
- 재귀 CTE 는 DB 별 문법이 갈려 쓰지 않았다. 3단계 제한이라 반복 조회로 충분하다.
- DB 는 `nullOnDelete` 지만 **앱에서 "하위 있으면 삭제 불가"를 막는다.** 자식이 최상위로 조용히 올라가는 건 사고다.

### 배송비 정책

- **활성 기본 정책은 항상 정확히 1개.** DB 제약으로 표현이 안 돼 라이브러리에서 강제한다. 삭제·비활성화·기본해제를 전부 막았고, 옮기려면 다른 정책을 기본으로 지정하면 자동으로 이전된다.
- 무료배송 기준 `0` 은 막았다. "항상 무료"는 `base_fee = 0` 으로 표현하는 게 의도가 분명하다.
- **`calculateFee()` 는 순수 계산이다.** 인자로 라인 배열만 받으므로 주문 라이브러리·커맨드·테스트 어디서든 쓴다.
- **무료배송 기준은 "유료배송 상품 합계" 기준이다.** 주문 총액이 아니다 — 무료배송 상품이 임계금액을 채워주면 정책 의도와 어긋난다. 바꾸려면 `calculateFee()` 한 줄.
- 정책이 섞이면 `base_fee` 가 가장 비싼 정책을 적용한다. 주문당 배송비는 1건이다.

### 상품 · 옵션 · 조합

- **조합은 프론트에서 "옵션 값 라벨의 배열"로 넘어온다.** 새로 만든 값은 아직 id 가 없기 때문이다. 라벨 → id 해석은 서버가 한다.
- **조합 매칭 열쇠는 signature** (`'빨강 / S'`). 옵션 값이 추가돼도 기존 조합의 id·재고·예약이 보존된다. 옵션 손대기 전에 찍어둬야 한다 (밟으면 아픈 곳 §8).
- 옵션 그룹은 **순번(`sort_order`)으로 매칭**한다. 이름을 바꿔도 같은 자리면 같은 그룹이다.
- **옵션 없는 상품도 조합을 1개 만든다.** 주문·장바구니가 항상 variant 를 가리키면 분기가 사라진다.
- 검색은 `whereLike(..., caseSensitive: false)` 를 쓴다. `ILIKE` 는 PostgreSQL 전용이라 금지 (CLAUDE.md §5.2).
- `withSum('variants as stock_total', ...)` 으로 목록의 재고 합계를 한 번에 가져온다 — 상품마다 조합을 도는 N+1 을 피한다.
- **TODO:** `orders` 생성 후 `ProductLibrary::delete()` 에 "주문 이력 있으면 삭제 불가, HIDDEN 안내" 추가. 소프트 삭제를 안 쓰기로 했으므로 이 가드가 이력 보호의 핵심이다.
### 상품 이미지

- **저장소는 `config('shop.image.disk')` 가 정한다.** 로컬 `public`, 운영 `s3`. `.env` 의 `SHOP_IMAGE_DISK` 한 줄로 바꾼다.
  - DB 에는 **상대 경로만** 넣고 URL 은 `Storage::disk(...)->url()` 로 만든다. 그래서 디스크를 바꿔도 데이터 마이그레이션이 없다 — 파일만 옮기면 된다.
  - S3 첫 사용 시 `composer require league/flysystem-aws-s3-v3` 가 필요하다. 안 깔면 "Driver [s3] not supported" 가 난다.
- **Windows 에서 `php artisan storage:link` 는 Junction 으로 만들어진다.** 관리자 권한이 필요 없다. (심볼릭 링크였다면 개발자 모드나 관리자 권한이 필요했다.)
- **파일 삭제와 DB 행 삭제의 순서가 중요하다.** 항상 **DB 행을 먼저** 지운다. 파일 삭제가 실패하면 고아 파일이 남을 뿐이지만, 반대로 하면 깨진 이미지를 가리키는 행이 남아 화면이 망가진다.
- **상품 삭제 시 파일까지 지운다** (`ProductImageLibrary::deleteAllFor`). DB 는 cascade 로 행만 지운다 — 이걸 빼면 storage 가 조용히 부풀어 오른다.
- 대표 이미지는 `products.thumbnail_path` 에 비정규화한다. 목록에서 이미지 테이블을 조인하지 않으려는 것이다. 대표가 바뀌거나 삭제되면 자동으로 동기화·승계된다.
- 업로드는 **상품이 존재해야** 가능하다. 등록 직후 수정 화면으로 보내는 이유가 이것이다 — 상품 없이 먼저 올리면 등록 취소 시 고아 파일이 남는다.
- 검증 규칙(확장자·용량·장수)은 `config/shop.php` 가 원천이다. FormRequest 에 숫자를 박지 않는다.

### 고객 상품 화면

- **관리자와 같은 `ProductLibrary` 를 쓰고 메서드만 나눴다** — `getAdminList`/`getSaleList`, `getDetail`/`getSaleDetail`. 조회 로직을 두 벌 짜지 않는다 (CLAUDE.md §4.2).
- **고객에게 재고 숫자를 내리지 않는다.** `sold_out` / `purchasable` 불리언만 준다. 경쟁사에 재고를 노출할 이유가 없다.
- **조합형 옵션 선택은 전부 프론트 계산이다.** 서버는 조합 목록(`option_value_ids`)만 준다.
  - 1단계 선택 → 그 값을 포함하는 variant 들만 남기고 → 거기 등장하는 2단계 값만 후보로 노출
  - **없는 조합은 애초에 variant 가 없어 후보에서 빠진다** — 별도 처리가 필요 없다
  - 그 값을 골랐을 때 살 수 있는 조합이 하나도 없으면 비활성 + 취소선
  - 앞 단계를 바꾸면 **뒤 단계 선택을 전부 비운다.** 안 그러면 존재하지 않는 조합이 확정된 것처럼 보인다
- **밟은 버그:** 상품이 배송비 정책을 안 고르면 `shippingPolicy` 가 null 이라 화면에 **"배송비 0원"** 이 떴다. 실제로는 기본 정책이 적용되어 결제 때 부과된다. `shippingInfo()` 에서 기본 정책으로 폴백하게 고쳤다. **null 을 그대로 화면에 내리면 금액이 거짓말을 한다.**
- 상세의 배송비는 "이 상품만 샀을 때" 안내일 뿐이다. **실제 청구액은 주문 시 `ShippingPolicyLibrary::calculateFee()` 가 정한다** — 여러 상품이 섞이면 달라진다.
- 카테고리 필터는 **하위 카테고리까지 포함**한다 (`CategoryLibrary::subtreeIds`). '의류' 를 고르면 '상의', '티셔츠' 상품도 나와야 한다.
- 헤더 카테고리 네비는 `HandleInertiaRequests` 공유 데이터다. 관리자 경로에서는 클로저가 평가되지 않는다.
- slug 가 한글이라 링크에 `encodeURIComponent()` 를 쓴다. 라우트 파라미터는 Laravel 이 자동 디코딩한다.

### 장바구니

- **`CartLibrary` 는 세션을 모른다.** 누구의 장바구니인지는 `App\Support\CartOwner` 값 객체로 받는다.
  세션을 만지는 유일한 지점은 `App\Http\Support\CartOwnerResolver` 다. 덕분에 커맨드·테스트에서 그대로 쓸 수 있다 (CLAUDE.md §4.2).
- **비회원 토큰은 세션에 담긴다.** 로그인 시 `session()->regenerate()` 는 **ID 만 바꾸고 데이터는 유지**하므로 토큰이 살아남는다. 이게 로그인 직후 병합이 가능한 이유다.
- 병합은 `Illuminate\Auth\Events\Login` 리스너(`MergeGuestCartOnLogin`)가 한다. Fortify 도 결국 이 이벤트를 쏘므로 한 곳에서 처리된다. **Laravel 11+ 는 `app/Listeners` 를 자동 등록**하므로 별도 배선이 없다 (`php artisan event:list` 로 확인).
  - 병합 후 **세션 토큰을 지운다.** 안 지우면 다음 요청에서 빈 비회원 장바구니가 다시 생긴다.
  - 합칠 때 상한(99)을 넘으면 잘라낸다. 병합 때문에 로그인이 실패하면 안 된다.
- **장바구니는 재고를 예약하지 않는다.** 여기 재고 확인은 안내용이고, 진짜 판정은 주문 트랜잭션 안에서 다시 한다 (schema-draft.md §7).
- **가격을 저장하지 않는다.** `summary()` 가 매번 현재가로 계산한다. 스냅샷은 주문 시점에만 뜬다.
- 담아둔 사이 품절되거나 재고가 줄 수 있다. `summary()` 가 `purchasable` / `exceeds_stock` / `has_issue` 를 내려 화면이 주문 버튼을 막는다.
- 배송비는 장바구니에서도 **`ShippingPolicyLibrary::calculateFee()` 같은 계산기**를 쓴다. 화면마다 다른 금액이 나오면 안 된다.
- `unique(cart_id, product_variant_id)` 로 같은 조합이 두 줄이 되지 않게 DB 에서 막고, `firstOrNew` 로 수량을 합친다.

### 쿠폰

- **`user_coupons.order_id` 는 아직 없다.** `orders` 테이블이 없어서 주문 단계에서 별도 마이그레이션으로 붙인다 (파일 하나 = 목적 하나, CLAUDE.md §5.3).
- **`expires_at` 은 발급 시점에 확정 저장한다.** 마스터의 `valid_days` 를 나중에 바꿔도 이미 발급된 쿠폰의 만료일은 안 변한다. 주문 스냅샷과 같은 원칙이고, 실제로 검증했다.
- **`valid_days`(발급일 기준)와 `valid_until`(절대 기간)은 다른 축이다.** 둘 다 있으면 더 이른 쪽이 만료일이다. 화면에도 이 설명을 적어뒀다.
  - **기간을 하나도 안 정하면 막는다.** 무기한 쿠폰은 대개 실수다.
- **정률 쿠폰에 상한(`max_discount_amount`)이 없으면 경고를 띄운다.** 고가 상품에서 할인액이 무한정 커진다. 막지는 않되 눈에 띄게 했다.
- 정률 할인은 **버림**(`intdiv`)이다. 올림은 가맹점 손해, 반올림은 합계가 어긋날 때 설명하기 어렵다.
- 할인은 **상품 합계에만** 적용하고 합계를 넘지 않는다. 배송비는 할인 대상이 아니다 (§8.3).
- 쿠폰 코드는 **대문자로 통일 저장**하고 조회 시에도 대문자로 맞춘다. 고객이 소문자로 입력해도 받아진다.
- **쿠폰은 삭제하지 않는다.** 라우트 이름은 `destroy` 지만 실제 동작은 `is_active = false` 다. 사용 이력이 매출과 엮인다.
- 발급이 시작된 쿠폰의 **발급 방식은 못 바꾼다.** SIGNUP 을 CODE 로 바꾸면 이미 받은 사람과 규칙이 어긋난다.
- 가입쿠폰 자동발급은 `Registered` 이벤트 리스너다. **한도 초과 등으로 실패해도 회원가입은 성공해야 한다** — 예외를 삼키고 로그만 남긴다.
- 비회원은 쿠폰을 가질 수 없다(`user_coupons.user_id` 필수). 그래서 쿠폰함 라우트만 `auth` 미들웨어를 건다.

### 알아둘 것 — 고객 로그아웃이 관리자 세션도 끊는다

같은 브라우저에서 관리자와 고객으로 동시에 로그인한 상태에서 **고객 로그아웃을 하면 관리자도 로그아웃된다.**
Fortify 의 로그아웃이 `session()->invalidate()` 로 세션 전체를 지우기 때문이다.

**버그가 아니라 의도된 보안 동작이다.** 개발 중 관리자 화면이 갑자기 로그인으로 튕기면 이걸 의심할 것.

### PostgreSQL 전환 (2026-08-20)

- **마이그레이션 17개가 무수정으로 통과했다.** §5 이식성 규칙을 처음부터 지킨 값을 여기서 받았다. 고칠 게 하나도 없었다.
- `pg_hba.conf` 가 `scram-sha-256` — 모든 접속에 비밀번호가 필요하다. **비대화형 셸에서 `psql` 을 그냥 부르면 입력을 기다리며 멈춘다.** `PGPASSWORD` 환경변수를 쓴다. (실제로 한 번 걸려서 프로세스를 죽였다.)
- `GRANT ALL ON SCHEMA public` + `ALTER SCHEMA public OWNER TO` 를 빠뜨리면 마이그레이션이 테이블을 못 만든다. PostgreSQL 15부터 `public` 스키마 기본 CREATE 권한이 회수됐기 때문이다.
- **`->after()` 는 PostgreSQL 도 지원하지 않는다.** MySQL 전용이다. CLAUDE.md §5.2 에 "PostgreSQL 지원" 이라고 잘못 적어뒀던 것을 고쳤다.
- **전환했다고 이식성 규칙을 놓지 않는다.** `DB_CONNECTION=sqlite` 로 되돌릴 수 있는 상태를 유지한다.

### 주문 · 재고 예약

- **주문 생성은 한 트랜잭션이다:** 조합 잠금 → 가격 재계산 → 쿠폰 확정 → 주문·항목 생성 → 예약 → 장바구니 비우기.
  - 하나라도 실패하면 전부 롤백된다. 실제로 재고 부족 케이스에서 예약이 늘지 않는 것을 확인했다.
- **잠근 뒤에 가격을 다시 읽는다.** 장바구니 요약은 잠금 전 값이라, 그 사이 관리자가 가격을 바꿨을 수 있다.
- **조합은 항상 id 오름차순으로 잠근다** (`StockLibrary::lockVariants`). 순서가 엇갈리면 두 주문이 서로를 기다리는 데드락이 난다.
- **예약 해제는 멱등하다.** `orders.stock_released_at` 이 있으면 아무것도 하지 않는다. 2차 호출이 `false` 를 반환하고 예약이 음수가 되지 않는 것을 확인했다.
- 결제 확정(`markPaid`)은 `stock_released_at` 도 채운다 — 예약이 실물로 바뀌었으니 해제 대상이 아니다.
- **취소는 상태에 따라 다르게 동작한다.** `PENDING` 이면 예약만 풀고(실물 불변), `PAID` 면 실물을 되돌린다.
- 주문번호는 앱에서 만든다(`ORD` + 날짜 + 랜덤). DB 시퀀스에 의존하지 않는다 (CLAUDE.md §5.1).
- 비회원 주문조회는 **주문번호 오류와 비밀번호 오류를 구분하지 않고**, IP 기준 5회 스로틀링을 건다. 주문 존재 여부를 흘리지 않기 위해서다.
- **`shop:expire-orders` 가 돌지 않으면 재고가 조용히 잠긴다.** `routes/console.php` 에 5분마다로 등록했지만, **스케줄러 프로세스가 실제로 떠 있어야** 한다.
- `--check-drift` 로 예약 정합성을 점검한다. **자동 수정하지 않고 보고만 한다** — 어긋났다면 원인을 봐야 한다.

### 결제 — 무통장입금

- **결제 기한은 수단마다 다르다.** `orders.payment_due_at` 에 주문 시점 확정 저장한다.
  - **무통장 1일**(주문 당일 자정까지), 카드 30분. `config/shop.php` 의 `payment.due`.
  - **고정 TTL 을 쓰면 무통장 주문이 전부 자동취소된다.** 사람이 은행에 가야 하는 시간을 30분으로 잡을 수 없다.
  - 기간을 늘리면 재고가 그만큼 오래 잠긴다. 회전율과의 맞교환이라 `.env` 의 `SHOP_BANK_TRANSFER_DUE_DAYS` 로 조정한다.
- **계좌 정보는 `payments` 에 스냅샷으로 복사한다.** 관리자가 계좌를 바꿔도 이미 안내한 주문의 계좌는 불변이다. 주문 스냅샷과 같은 원칙이고 검증했다.
- 같은 주문에 살아 있는(READY) 요청이 있으면 새로 만들지 않는다. 새로고침마다 결제 행이 쌓이는 것을 막는다.
- **입금 확인은 누가 눌렀는지 남긴다** (`confirmed_by_admin_id`). 수동 처리는 책임 소재가 중요하다.
- 확인 시 **주문 상태를 다시 본다.** 그 사이 취소됐다면 결제완료로 만들지 않는다.
- 주문이 취소되면 `OrderLibrary::cancel()` 이 살아 있는 결제 요청도 함께 닫는다. 안 그러면 관리자 목록에 유령 건이 남는다.
- **`SETTING_BANK`(계좌설정)는 운영자 권한에서 제외했다.** 입금 계좌를 바꾸면 고객 송금이 그 계좌로 간다 — 사기 벡터다. 무통장처리(`PAYMENT_DEPOSIT`)는 운영 업무라 열어뒀다.
- **입금 안내는 실제로 발송되지 않는다.** `DepositNotifier` 가 로그에만 남긴다(로컬 메일이 log 드라이버인 것과 같다). 카카오·SMS 를 붙이려면 그 클래스에 채널 메서드를 더하고 `config('shop.payment.notify_channels')` 에 이름을 추가한다. 호출부는 안 건드린다.
- 안내 발송은 **트랜잭션 밖**이다. 발송이 느리거나 실패해도 주문은 이미 안전하고, 계좌는 주문완료 화면에도 표시된다.
- `OrderLibrary` ↔ `PaymentLibrary` 순환 참조를 피하려고 기한 계산을 `App\Support\PaymentDueCalculator` 로 뺐다.

### 배송

- **주문 상태와 배송 상태를 함께 움직인다.** 한쪽만 바꾸면 화면마다 다른 말을 하게 된다.

  ```
  PAID → PREPARING → SHIPPING → DELIVERED   (orders.status)
         READY     → SHIPPING → DELIVERED   (shipments.status)
  ```

- **송장을 찍는 순간 출고로 본다.** `ship()` 이 `shipments` 를 채우고 주문을 `SHIPPING` 으로 바꾼다.
- `PREPARING` 단계는 선택이다. `PAID` 에서 바로 출고해도 된다 — 실무에서 준비중 표시를 건너뛰는 경우가 많다.
- **출고취소(`revertShipping`)를 뒀다.** 송장을 잘못 찍는 일은 반드시 생긴다. 다만 **배송완료된 건은 되돌리지 않는다** — 고객이 이미 받았다.
- 배송중 주문은 **고객이 취소할 수 없다** (`OrderStatus::isCancelableByCustomer` 가 PENDING/PAID 만 허용). 별도 코드 없이 기존 규칙으로 막힌다.
- **택배사 목록은 `config/shop.php` 의 `shipping.carriers`.** 코드는 대문자이며 `shipments.carrier` 가 이 값을 저장하므로 한번 정하면 바꾸지 않는다.
  - ⚠ **`tracking_url` 은 택배사 사정으로 바뀐다.** 운영 투입 전 실제 송장번호로 열어 확인할 것. 코드에 넣어둔 URL 은 검증되지 않았다.
  - `DIRECT`(직접배송)처럼 URL 이 없으면 조회 링크를 아예 렌더하지 않는다.
- 송장번호는 `rawurlencode` 해서 URL 에 넣고, 링크에 `rel="noopener"` 를 붙인다.
- 고객 화면에는 **출고 전 배송정보를 내리지 않는다** (`customerView` 가 `READY` 면 null). 송장도 없는데 '배송정보' 칸이 뜨면 혼란만 준다.
- 주문당 1건이라 `shipments.order_id` 에 unique 를 걸었다. 부분배송을 열 때 이 제약을 푼다.
- `present()` 가 배송을 읽으므로 주문 조회 경로에 `with(['items', 'shipment'])` 를 걸어 N+1 을 막았다.

### 관리자 주문관리

- **배송관리와 역할이 다르다.** 배송관리는 결제 이후 배송 단계만, 주문관리는 **모든 상태**를 보고 상세 확인·강제취소를 한다.
- **취소 권한이 고객보다 한 단계 넓다:**

  | | PENDING | PAID | PREPARING | SHIPPING 이후 |
  |---|---|---|---|---|
  | 고객 | ✓ | ✓ | ✗ | ✗ |
  | 관리자 | ✓ | ✓ | **✓** | ✗ |

  `OrderStatus::isCancelableByAdmin()` 으로 분리했고 `cancel(..., byAdmin: true)` 로 전달한다.
- **출고 이후는 관리자도 못 막는다.** 물건이 이미 나갔으므로 취소가 아니라 반품·환불 절차다. 에러 메시지도 그렇게 안내한다.
- **강제 취소는 사유가 필수다.** 나중에 왜 취소됐는지 설명할 수 있어야 한다. 메모는 `관리자 취소: {사유}` 로 저장된다.
- 상세 화면에 **결제 이력·배송·재고 변동을 한 곳에 모았다.** 문의가 들어왔을 때 화면 여러 개를 오가지 않게 하려는 것이다. 취소하면 재고 변동에 `입고·반품 +N` 이 찍혀 복구가 눈에 보인다.
- 목록에서 **미결제인데 기한이 지난 주문**을 빨갛게 표시한다. 스케줄러가 곧 취소할 건이다.

### 회원관리 · 1:1 문의

- **상세는 모달이지만 `?selected=` 쿼리로 연다.** 모달을 컴포넌트 상태로만 두면 새로고침·뒤로가기·링크 공유가 전부 깨진다. URL 에 담으면 Inertia 가 알아서 처리한다.
- **상세 prop 은 클로저다.** 목록만 볼 때는 평가되지 않는다 — 회원 상세는 주문·결제·문의·쿠폰을 다 모으므로 매번 만들면 낭비다.
- 목록의 '주문' 은 `1 / 2` 형태 — **결제된 건 / 전체 건**이다. 취소·미결제를 빼야 실제 구매 이력이 보인다. 구매금액도 같은 기준이다.
- **이메일을 바꾸면 인증이 자동 해제된다.** 새 주소는 확인된 적이 없다. 반대로 관리자가 수동 인증 처리도 할 수 있다 — 고객이 메일을 못 받는 경우가 있다.
- 메모는 **고객에게 보이지 않는다.** 작성자와 시각이 남는다.
- 문의에 주문을 붙일 때 **본인 주문인지 확인**한다. 남의 주문번호를 붙이면 그 주문 정보가 노출된다.
- 고객 화면에는 **답변자 이름을 내리지 않는다.** 관리자 이름이 고객에게 갈 이유가 없다.
- 비회원은 문의를 남길 수 없다 — 답변을 전달할 곳이 없고 본인 확인도 안 된다.
- 문의 답변 권한은 `MEMBER_LIST` 를 따른다. 회원 상세 안에서 처리하기 때문이다.
- **밟은 것:** 시드에서 `email_verified_at` 이 `User` 의 `Fillable` 에 없어 `updateOrCreate` 로 안 들어갔다. 앱 로직은 `markEmailAsVerified()` / 직접 대입이라 무관하지만, **테스트 데이터를 만들 때 또 걸린다** (밟으면 아픈 곳 §8과 같은 함정).

### 반품 · 교환

- **취소와 반품의 경계는 '출고'다.** 출고 전은 `OrderLibrary::cancel()`, 출고 후는 `ReturnLibrary`.
  주문 상태가 겹치지 않으므로 고객 화면에서 두 버튼이 동시에 뜨는 일은 없다.
- **항목·수량 단위다.** 주문당 여러 건이 생길 수 있고, 같은 주문 항목을 나눠서 반품할 수 있다.
  남은 신청 가능 수량은 `remainingQuantities()` 가 계산한다.
- **반려된 건은 수량 점유를 푼다** (`ReturnStatus::occupiesQuantity()`).
  반려당한 고객이 사유를 바꿔 다시 신청할 수 있어야 한다. 고객의 '신청 취소' 도 같은 자리로 보낸다.
- **재고와 돈은 `complete()` 한 곳에서만 움직인다.**
  물건을 받기 전에 환불하면 회수하지 못한다. 그래서 `RECEIVED` 를 거치지 않으면 완료할 수 없다.
- **입고완료 건은 반려할 수 없다.** 물건이 창고에 있는데 반려하면 그 물건이 장부에서 사라진다.
  되돌리려면 처리완료하거나 별도로 재출고한다.
- **귀책(`responsibility`)이 배송비를 정한다.** 사유가 기본값을 제시하고(`defaultResponsibility()`),
  **최종 결정은 관리자가 승인할 때 한다** — 변심으로 접수됐는데 실제로는 불량인 경우가 흔하다.
  - 고객 귀책 → 왕복 배송비(`config('shop.return.shipping_fee')`) 차감
  - 판매자 귀책 + 전량 반품 → 최초 배송비까지 환불
- **`restock` 은 물건을 봐야 정한다.** 불량·파손은 기본 `false` 다 (`defaultRestockable()`).
  이걸 무심코 켜면 하자품이 재고로 돌아가 다시 팔린다. 입고 시점에 다시 확인받는다.
- **금액은 승인 시점 스냅샷이다.** 나중에 배송비·쿠폰 정책이 바뀌어도 이미 승인한 환불액은 안 변한다.
  승인 전 화면에는 **서버가 귀책 두 경우를 모두 계산해** 내려준다 — 화면에서 다시 계산하면 규칙이 두 벌이 된다.
- **쿠폰은 전량 반품일 때만 되살린다.** 부분 반품에서 되살리면 남은 주문에 할인이 적용된 채로 쿠폰을 다시 쓴다.
- 교환은 **같은 상품의 다른 조합**으로만 된다. 다른 상품은 금액이 달라져 반품 후 재주문이 맞다.
  교환 재고 확인은 접수가 아니라 **`complete()` 에서 잠근 채로** 한다 — 그 사이 재고가 바뀐다.
- **교환 송장은 `shipments` 에 넣지 않았다.** `shipments` 는 주문당 1건(최초 배송)이라
  두 번째 행을 허용하면 `Order::shipment()` 부터 의미가 흔들린다.
  회수·재발송 송장은 `order_returns` 에 직접 붙였다.
- 교환은 정산이 없다(`refund_amount = 0`). `shipping_deduction` 만 남겨
  "고객이 부담할 배송비" 를 관리자가 알 수 있게 했다 — **실제 수납은 시스템 밖이다.**
- 반품 배송비가 상품값보다 크면 환불액이 음수가 된다. **추가 청구 수단이 없어 0 으로 막았다.**
  부족분은 관리자 메모로 관리한다. PG 를 붙이면 여기를 다시 봐야 한다.
- 신청 기한은 배송완료일 + `config('shop.return.days')`(기본 7일)다.
  **관리자 대행 접수(`byAdmin: true`)는 기한을 보지 않는다** — 하자는 법정 기한이 더 길고 예외는 사람이 판단한다.
- 아직 배송중(`SHIPPING`)이면 기한이 시작되지 않은 것으로 보고 신청을 받아둔다.

### 데모 데이터 (`shop:demo`)

- **시더를 두 층으로 갈랐다.** `DatabaseSeeder` 는 운영에도 필요한 것만(관리자·배송비 정책·계좌),
  `DemoSeeder` 는 화면을 채우는 것만. 섞어두면 운영 배포 때 데모 회원·주문이 따라 들어간다.
- **전부 라이브러리를 거쳐 만든다.** 상품을 `Product::create()` 로 만들면 slug 생성·조합 동기화가
  빠지고, 주문을 직접 만들면 재고 예약·쿠폰 사용처리가 빠진다. 그러면 **시드 데이터만
  앱이 만들어내는 데이터와 다른 모양**이 되어, 그 위에서 하는 화면 확인이 의미가 없어진다.
- 카탈로그에 일부러 섞어 둔 것들 — 각각 확인용이다:
  - `HIDDEN` 상품 1개 → 고객 목록에서 빠지는지
  - `SOLD_OUT` 상품 1개 → '품절' 배지
  - 재고 0 인 색상(경량 패딩 베스트 카키) → 옵션 1단계가 통째로 비활성되는지
  - 무료배송 상품 2개 → 배송비가 **유료 상품 합계** 기준으로만 계산되는지
  - 할인가 있는 상품 4개 → 목록의 가격 표기
  - 옵션 없는 상품(볼캡) → 조합이 1개만 생기는 경로
- 주문은 **상태를 골고루** 만든다(PENDING·PAID·PREPARING·SHIPPING·DELIVERED·CANCELED·REFUNDED).
  관리 화면이 전부 빈 목록이면 화면을 볼 수가 없다.
- **`DemoOrderSeeder` 는 쿠폰 주문의 `discount_total` 이 0 이면 예외를 던진다.**
  일부러 넣은 가드다 — 아래 §13 버그가 다시 나면 시드가 즉시 실패해서 알려준다.
- 상품 이미지는 GD 로 그린다(`DemoImageFactory`). `UploadedFile::fake()->image()` 는
  빈 회색 네모라 목록 화면 감각을 볼 수 없었다. 그러데이션 + 코드 라벨로 타일이 구분되게 했다.
  **파스텔 색을 그대로 쓰면 안 된다** — 끝색을 0.62 로 눌러야 그리드에서 서로 구분된다.
- `shop:demo --fresh` 는 `storage/app/public/products` 를 먼저 지운다.
  DB 만 초기화하면 이전 회차 이미지 파일이 계속 쌓인다.

### 대시보드 · 통계

- **대시보드 맨 위는 '처리 대기'다.** 매출보다 먼저 온다 — 관리자가 로그인해서
  제일 먼저 알아야 할 건 "오늘 내가 손댈 일" 이다. 각 카드는 해당 화면으로 바로 간다.
  건수가 0 인 항목은 아예 안 보여준다. 0 이 여섯 줄 늘어서면 볼 게 없는데 화면만 찬다.
- **매출 기준은 `OrderStatus::countsAsSale()` 하나로 모았다** (PAID·PREPARING·SHIPPING·DELIVERED).
  결제 전은 돈이 안 들어왔고 취소·환불은 나갔다. 이 기준이 흩어지면
  대시보드와 통계 화면의 숫자가 서로 안 맞는다.
- **날짜 경계는 `config('shop.timezone')`(Asia/Seoul)로 끊는다.** DB 는 UTC 라
  그냥 자정으로 자르면 한국 기준 오전 9시에 날짜가 바뀌어 전날 저녁 주문이 오늘로 잡힌다.
- **집계는 PHP 컬렉션에서 한다.** `GROUP BY DATE(...)` 는 DB 마다 함수가 갈려 §5.1 위반이다.
  기간 안의 행을 읽어 `groupBy` 로 묶는다. **주문이 수만 건이 되면 이 방식이 버겁다** —
  그때는 일별 집계 테이블을 두고 여기서는 읽기만 하도록 바꾼다.
- **매출 없는 날도 0 으로 채운다.** 빈 날을 건너뛰면 그래프의 가로축이 거짓말을 한다.
- **카테고리·상품별 금액은 '할인 전 상품 금액'이다.** 주문 항목 합계라
  위의 '결제 매출'과 쿠폰 할인·배송비만큼 차이가 난다. 화면에 명시해뒀다 —
  안 적으면 숫자가 안 맞는다는 문의가 반드시 들어온다.
- 차트는 **라이브러리 없이 div 막대**로 그렸다(`BarSeries.vue`). 막대 하나 그리자고
  번들에 수백 KB 를 얹을 이유가 없다.
- 재고 부족은 `실물 − 예약 <= 5`. 컬럼 하나로 비교할 수 없어 후보를 넉넉히
  가져와 PHP 에서 거른다.

### 추천 · 최근 본 상품

- 알고리즘은 **함께 구매(item-to-item)** 하나다. 내가 산 상품이 담겼던 주문들에서
  다른 상품을 빈도순으로 센다. 부족하면 같은 카테고리 인기 → 전체 인기로 채운다.
  **추천 줄이 한 칸만 차는 게 제일 안 좋다** — 화면이 덜 만들어진 것처럼 보인다.
- **품절·숨김 상품은 추천에서 뺀다** (`purchasableFrom`). 상품 목록은 품절을
  배지 달고 보여주는 게 맞지만, **추천은 클릭해서 살 수 있어야 추천이다.**
  실제로 처음엔 품절 니트가 추천에 떴다.
- 이미 산 상품도 뺀다. 방금 산 걸 다시 추천하면 추천처럼 보이지 않는다.
- **문구까지 서버가 정한다.** 로그인·구매이력에 따라 '회원님을 위한 추천' /
  '많이 찾는 상품' 이 갈리는데, 화면에서 분기하면 "왜 이 문구가 나오는가" 가 두 곳에 흩어진다.
- **최근 본 상품은 쿠키다** (`app/Support/RecentlyViewed`). 비회원도 동작해야 하고
  로그인 전후로 끊기면 오히려 이상하다. 기기 간 동기화가 필요해지면 그때 테이블을 만든다.
  - 쿠키 값은 사용자가 고칠 수 있다 → **정수만 남기고 전부 버린다.**
  - 만료는 **분 단위**다. 초로 착각하면 30일이 30분이 된다.
  - 상품 상세에서는 **방금 본 상품을 뺀다.** 안 빼면 자기 자신이 첫 칸에 뜬다.
- `RecentlyViewed` 는 `app/Support` 에 있다. Request·Cookie 에 의존하므로
  라이브러리 규칙(§4.2)상 `app/Libraries` 에 둘 수 없다 — 라이브러리에는 id 배열만 넘긴다.
- 캐시를 넣지 않았다. 데이터가 바뀌어도 화면이 안 변해 개발 중 혼란만 준다.
  트래픽이 붙으면 `popularIds()` / `coPurchasedWith()` 부터 캐시한다.

### 바로구매

- **장바구니를 거치지 않는다.** 세션에 조합 하나(`direct_order`)만 담고 주문서로 간다.
  담아둔 장바구니는 **그대로 남는다** — 바로구매인데 장바구니까지 결제되면 사고다.
- 주문 생성 경로는 **하나로 유지했다.** `OrderLibrary::create()` 를 private 로 두고
  `createFromCart()` / `createDirect()` 가 같은 본체를 부른다. 차이는 딱 두 가지 —
  요약을 어디서 받느냐, 끝나고 장바구니를 비우느냐. 경로를 두 벌로 나누면
  재고 잠금·쿠폰 확정·예약 순서가 반드시 어긋난다.
- 라인 모양도 공유한다. `CartLibrary::lineFor()` 를 장바구니 요약과
  `directSummary()` 가 같이 쓴다. 모양이 갈리면 배송비 계산부터 틀어진다.
- **세션 정리가 핵심이다.** 안 지우면 다음 장바구니 주문을 가로챈다.
  - 주문 완료 시 `forget`
  - **장바구니 페이지에 들어오면 `forget`** — 장바구니로 돌아왔다는 건 바로구매를 벗어났다는 뜻이다
- `return_to` 는 **`/` 로 시작하는지 확인한다.** 안 하면 열린 리다이렉트가 된다.

### 바로구매의 로그인 요구 ⚠

**이 경로만 로그인을 요구한다.** 비로그인이면 `url.intended` 에 상품 주소를 넣고
로그인 화면으로 보낸다 — Fortify 의 `redirect()->intended()` 가 읽어 되돌려준다.

**비회원 주문 허용(schema-draft.md §0)과 부딪히는 지점이다.**
장바구니 → 주문서 경로는 비회원도 그대로 쓸 수 있게 뒀다.
바로구매에도 비회원을 허용하려면 `Store/OrderController::direct()` 의
`$request->user() === null` 분기만 빼면 된다 — 라이브러리는 이미 비회원을 받는다.

### 상품 후기 · 문의 · 상세 이미지 · 상담 채널

- **상세 이미지는 테이블을 새로 만들지 않았다.** `product_images.type` 으로 갈랐다.
  갤러리는 대표(썸네일) 개념이 있고 상세는 순서만 있다 — `ProductImageType` 이 그 차이를 갖고 있다.
  **업로드·정렬에 용도를 안 넘기면** 상세 이미지가 대표로 지정되어 목록 썸네일이 바뀐다.
  `reorder()` 가 같은 용도 안에서만 동작하도록 소유권과 함께 검사한다.
- **후기는 구매자만.** 근거는 `order_items` 이고, `order_item_id` 가 unique 라
  주문 항목당 한 건이다. DB 제약과 앱 검증을 **둘 다** 뒀다 —
  화면에 '작성' 버튼이 뜬 뒤 실패하면 사용자 입장에서 이상하므로 앱에서도 미리 거른다.
- **후기는 지우지 않고 숨긴다.** 고객이 '삭제' 를 눌러도 숨김이다.
  평점 이력이 구매 이력과 엮여 있어 지우면 설명이 안 된다.
- 고객 화면은 **이름을 가린다**(`김서연` → `김*연`), 관리자 화면은 실명이다.
  후기·문의가 공개 글이기 때문이다.
- **상품 문의는 1:1 문의와 다른 테이블이다.** 붙는 대상(상품/주문)과
  공개 범위(공개/비공개)가 다르고, 구매 여부도 다르다 —
  문의는 **사기 전에** 하는 것이라 구매를 요구하지 않는다.
- **상담 채널은 URL 만 받는다.** 실시간 상담을 자체 구현하지 않았다 —
  상담원이 붙어 있어야 의미가 있고 그건 운영의 문제다.
  `SHOP_SUPPORT_URL` 이 비어 있으면 버튼이 아예 안 뜬다. 네이버 톡톡·카카오 채널 모두 같은 자리에 붙는다.
- 별점은 **반쪽 별을 그리지 않는다.** 4.3 과 4.5 를 이 크기에서 구분할 수 없고,
  SVG 마스크를 넣을 만큼의 값이 없다. 반올림해 채운다.
- **후기가 0건이면 별을 아예 안 그린다.** 빈 별 5개는 '0점' 처럼 보인다.

### 회원 배송지록 · 프로필 확장

- **회원 데이터가 실제로 어디 있는지 점검하다가 시작한 작업이다.** `users` 테이블이
  Fortify 스캐폴딩 그대로였다 — 주소·전화번호는 `orders` 스냅샷에만 있었고(매 주문마다
  새로 입력), 수신동의·마지막 로그인은 컬럼 자체가 없었다.
- **배송지는 `bank_accounts`·`shipping_policies` 와 같은 "기본 하나만 유지" 패턴을 쓰되
  전역이 아니라 회원별이다.** 그리고 그 두 테이블과 달리 **기본이 하나도 없는 상태가
  정상**이다(가입 직후) — "기본이 반드시 있어야 한다" 는 불변식을 강제하지 않는다.
- **주문의 배송지 스냅샷 원칙은 그대로 지킨다.** `user_addresses` 는 "즐겨찾기" 일 뿐이고,
  원본은 여전히 `orders.address1` 등이다. 배송지록을 나중에 고쳐도 이미 낸 주문서는
  안 바뀐다.
- **동의는 boolean 이 아니라 시각을 저장한다.** 정보통신망법상 광고성 정보 전송에는
  "언제 동의했는지" 를 증명해야 한다. 껐다 켜면 시각이 새로 찍힌다(재검증 완료 —
  꺼짐→켜짐일 때만 갱신, 이미 켜진 상태를 다시 켜도 기존 시각을 유지하는지까지 확인).
- **로그인 시각은 `Illuminate\Auth\Events\Login` 이벤트를 듣는다.** 관리자는
  `AdminLoginController` 가 직접 `forceFill` 하므로(수동 인증), 리스너는 **`web` 가드일
  때만** 처리하고 `admin` 가드는 무시한다 — 두 계정 체계를 분리하는 CLAUDE.md §7.1 원칙을
  이벤트 레벨에서도 지킨다. (검증 중 리스너가 admin 값을 건드리는 것처럼 보인 적이 있었는데,
  `null?->eq(null)` 이 `null`(falsy) 을 반환하는 검증 스크립트 자체의 버그였다 — 실제로는
  guard 분리가 정확히 동작한다.)
- **주문서는 기본 배송지로 자동 채워지고, 직접 입력하면 '저장' 체크박스가 나온다.**
  이미 저장된 배송지를 골랐을 때는 체크박스를 안 보여준다 — 저장된 걸 또 저장할
  이유가 없다.
- **배송지 저장 실패가 주문을 막지 않는다.** 개수 초과 같은 사유로 저장에 실패해도
  결제는 이미 끝난 뒤라 조용히 넘어간다. 부가 기능이 본 절차를 막으면 안 된다.

### 간편로그인 (카카오·네이버)

- **`users` 스키마는 그대로 두고 소셜 식별자만 별도 테이블로 뺐다.** `user_social_accounts`
  는 회원 1명에 여러 연동(카카오+네이버)을 허용하는 1:N 이고, `(provider, provider_user_id)`
  가 유니크다 — 같은 카카오 계정이 다른 회원에 중복 연동될 수 없다.
- **매칭 순서: ① 이미 연동된 소셜 계정 ② 제공자가 이메일을 줬으면 그걸로 로그인/가입
  ③ 안 줬으면 추가입력 화면.** ②에서 같은 이메일의 기존 회원에 연동만 더하지 않으면,
  비밀번호로 가입한 회원이 나중에 소셜로 로그인할 때마다 새 계정이 생긴다.
- **★ 이메일의 출처에 따라 처리가 갈린다 — 라이브러리 메서드를 둘로 나눈 이유가 이것이다.**
  - `linkWithVerifiedEmail()`: *제공자가 검증한* 이메일(네이버). 그 주소의 주인임을
    제공자가 보증하므로 **같은 이메일의 기존 회원에 연동만 추가**해도 안전하다.
  - `createWithUnverifiedEmail()`: *본인이 화면에서 직접 입력한* 이메일(카카오).
    **아무도 검증하지 않았으므로 기존 회원에 절대 붙이면 안 된다** — 붙이면 카카오 계정
    하나만 있으면 남의 이메일을 적어 넣는 것만으로 그 계정을 통째로 가져갈 수 있다.
    이미 쓰는 주소면 막고(그 계정으로 로그인한 뒤 연동하라고 안내), 새 회원만 만든다.
  - 처음에 `findOrCreate()` 하나로 두 경우를 다 처리하려다, 이메일 출처를 구분하지 않으면
    바로 이 계정 탈취가 열린다는 걸 깨닫고 갈랐다. **메서드 이름에 "verified/unverified"
    를 박아둔 건 다음에 이 구분을 잊지 않기 위해서다.**
- **카카오는 개인 개발자 앱에서 이메일을 아예 못 받는다.** 동의항목 화면에서
  `account_email` 이 "사용 안 함" 도 아니고 **"권한 없음"** — 설정 버튼조차 없다.
  비즈 앱 전환(사업자등록 필요)을 해야 열린다. 그렇다고 가입을 막으면 카카오 로그인이
  통째로 쓸모없어지므로, **모자란 항목만 본인에게 직접 받는 화면**(`SocialComplete`)을 뒀다.
  이메일 없이 임의 문자열(`kakao_1234@social.local` 같은)을 지어내지 않는다 — 실제로 그
  주소를 못 쓰는 사람인데 있는 것처럼 저장하면 나중에 알림·조회가 전부 거짓말이 된다.
- **추가입력 화면에 provider_user_id 를 넘기지 않는다.** 소셜 신원은 콜백에서 세션에
  넣어두고(`social_signup`) 거기서만 꺼낸다. 폼으로 받으면 아무 소셜 계정이나 자기
  것이라고 주장할 수 있다 — hidden input 이어도 마찬가지다.
- **소셜 가입 회원의 비밀번호는 임의값이다.** 컬럼이 NOT NULL 이라 뭔가는 넣어야 하는데,
  본인도 모르는 랜덤 문자열을 `Hash::make` 해서 채운다. 나중에 비밀번호 로그인을 쓰고
  싶으면 "비밀번호 찾기" 로 새로 정하면 된다 — 별도 "비밀번호 설정" 화면을 새로 안 만든다.
- **`email_verified_at` 도 이메일 출처를 따른다.** 제공자가 준 주소면 즉시 채우고(인증
  메일을 또 보내지 않는다), 본인이 입력한 주소면 null 로 두고 평소의 인증 메일을 보낸다 —
  그래야 비밀번호 가입 회원과 완전히 같은 상태가 되어 헤더의 "이메일 인증 필요" 배지와
  기존 인증 흐름이 그대로 작동한다.
- **`socialiteproviders/*` 패키지는 자기 서비스 프로바이더가 없다.** `SocialiteWasCalled`
  이벤트를 듣는 리스너가 `extendSocialite()` 로 직접 드라이버를 등록해줘야 한다
  (`ExpandSocialiteProviders`) — 이것도 여느 리스너처럼 `app/Listeners` 자동 등록에
  얹힌다, 밟으면 아픈 곳 §24 와 같은 이유로 `Event::listen()` 을 또 쓰지 않는다.
  (참고로 카카오 드라이버 클래스명은 `SocialiteProviders\Kakao\KakaoProvider` 다 —
  네이버(`SocialiteProviders\Naver\Provider`)와 이름 규칙이 달라서 처음에 오타로
  막혔다. `php artisan migrate` 조차 부팅 시점에 `SocialiteWasCalled` 를 쏘기 때문에
  클래스명이 틀리면 마이그레이션도 못 돈다 — 소셜 로그인과 전혀 상관없는 명령에서
  에러가 나서 원인 파악에 잠깐 헤맸다.)
- **버튼은 `.env` 에 Client ID 가 없으면 서버가 아예 안 내려준다.** `supportChannel`
  (네이버 톡톡 버튼)과 같은 패턴이다 — 로컬 데모 상태에서는 눌러도 실패할 버튼을
  화면에 남기지 않는다.
- **로그인 성공 처리는 `Auth::guard('web')->login($user)` 하나뿐이다.** 그 뒤로는
  비밀번호 로그인과 완전히 같은 이벤트 경로를 타서 `RecordUserLogin` 리스너가
  그대로 적용되고 `last_login_at` 도 자연히 찍힌다 — 소셜 로그인 전용 후처리를
  따로 만들지 않았다.

### 관리자 상단 알림 · 통계 집계 테이블 · 회원 전용 구매 (2026-08-25)

**관리자 상단 알림**

- **대시보드의 '처리 대기' 를 `AdminTodoLibrary` 로 빼서 헤더와 공유한다.** 두 곳에서
  각자 세면 반드시 어긋난다 — 같은 정의를 한 군데서만 쓴다.
- 항목을 두 개 늘렸다: **미답변 상품문의**, **답글 없는 후기**. 후기는 "미답변" 상태값이
  따로 없어서(상태는 노출/숨김뿐) `admin_reply` 가 비었는지로 판단하고, **숨긴 후기는
  세지 않는다** — 안 보이는 글에 답글을 달 이유가 없다.
- **권한 없는 항목은 알림에도 안 뜬다.** 사이드바에서 메뉴를 숨겨놓고 헤더 배지로 같은
  숫자를 흘리면 권한 분리가 무의미해진다(§7.5). 권한만 남긴 계정으로 실제 확인했다.
- **건수 0 인 항목은 목록에서 빼고, 전부 0 이면 배지를 아예 안 그린다.** 할 일이 없는데
  빨간 점이 떠 있으면 그때부터 아무도 안 본다.
- 관리자 화면마다 COUNT 쿼리가 몇 개 돈다. 전부 인덱스 걸린 status 컬럼이라 지금
  규모에선 문제없고, 느려지면 공유 데이터에 짧은 캐시를 씌우면 된다.

**일별 매출 집계 테이블**

- **`daily_sales_stats` 는 파생 데이터다.** 원본은 `orders`·`order_returns` 이고 언제든
  다시 만들 수 있다(`shop:aggregate-sales --all`). 숫자가 이상하면 원본을 고치고 재집계한다.
- **왜 이벤트가 아니라 배치인가.** 결제 시점에 집계를 갱신하면 항상 최신이지만 결제
  트랜잭션에 통계 쓰기가 끼어든다 — 통계가 실패하면 주문이 실패하거나 조용히 어긋난다.
  **매출 숫자가 몇 분 늦는 것보다 주문이 안전한 게 중요하다.**
- 대신 **화면에 "집계 기준 시각" 을 띄운다.** 이게 없으면 스케줄러가 죽어도 아무도 모른다 —
  주문은 정상인데 통계만 과거에 멈춘 상태가 제일 위험하다.
- 날짜별 `updateOrCreate` 라 몇 번을 돌려도 값이 누적되지 않는다. 스케줄러가 최근 3일을
  5분마다 다시 계산해도 안전한 이유다.
- **`stat_date` 는 KST 달력 날짜다.** UTC 자정으로 끊으면 한국 기준 오전 9시에 날짜가 바뀐다.
- 환불은 **주문일이 아니라 반품 처리완료일** 에 잡는다 — 돈이 실제로 나간 날에 다는 게 맞다.
- 데모 주문은 과거 날짜에 뿌려지므로 `shop:demo` 끝에 `--all` 재집계를 붙였다.
  안 그러면 주문은 있는데 집계 행이 없어서 **대시보드 매출이 0 으로 보인다.**
- 상품별·카테고리별은 아직 실시간이다. 상위 N개 형태라 상품×날짜 테이블이 따로 필요하다.

**회원 전용 구매 (§0 원칙 뒤집기)**

- 프로젝트 초기 확정 사항이던 "비회원 주문 허용" 을 폐지했다. `docs/schema-draft.md` §0·§4.2
  에 폐지 사실과 날짜를 남겼다 — **확정 사항을 조용히 바꾸면 나중에 코드와 문서가 싸운다.**
- **장바구니는 그대로 비회원도 쓴다.** 로그인을 요구하는 지점은 '담기' 가 아니라 '주문' 이다.
  담아두고 로그인하면 그대로 넘어오고(`MergeGuestCartOnLogin`), 주문서가 GET 이라
  auth 미들웨어의 intended URL 로 자동 복귀한다.
- **바로구매(POST)만 미들웨어를 안 걸고 컨트롤러에서 검사한다.** POST 는 intended URL 이
  referer 로 잡혀 돌아갈 자리가 부정확해지고, 안내 문구도 밋밋해진다. 실제 차단은 뒤이어
  거치는 checkout/store 의 auth 가 보장하므로 안전하다.
- **`orders.guest_password` 와 `/orders/lookup` 은 남겼다.** 정책 변경 전 비회원 주문을
  조회할 통로가 필요해서다. 다만 현재 DB 의 비회원 주문은 0건이라 사실상 죽은 코드다 —
  **헤더 링크만 뺐다**(새 방문자에게는 쓸모없는 메뉴라서). 완전 삭제는 되돌리기 어려워
  판단을 미뤘고 CLAUDE.md 에 정리 후보로 적어뒀다.
- `OrderLibrary::create()` 의 `?int $userId` 를 **`int $userId` 로 좁혔다.** 타입으로
  "비회원 주문은 이제 만들 수 없다" 를 못박아 둔다 — 주석보다 확실하다.

### 표시 시간대(KST) · 반응형 (2026-08-26)

- **저장은 UTC, 표시는 KST.** `App\Support\LocalTime` 하나를 통과시키는 방식으로
  라이브러리가 내보내는 `*_at` 55곳을 바꿨다. 저장 계층(`config('app.timezone')`)은
  손대지 않았다 — 바꿨다면 과거 데이터가 전부 9시간 틀어졌을 것이다(밟으면 아픈 곳 §27).
- **초는 버렸다**(`Y-m-d H:i`). 화면에서 의미가 없고, 기존 Vue 코드가 쓰던
  `.slice(0, 10)` / `.slice(0, 16)` 이 그대로 동작하는 길이라 손댈 곳이 없었다.
- **통계는 예외로 뒀다.** `StatLibrary` 의 날짜 경계와 `SalesAggregateLibrary` 는 이미
  자체적으로 시간대를 다룬다 — 여기에 변환을 또 씌우면 이중 변환이 된다.
- **주문번호의 날짜(`ORD20260825...`)도 KST 로 바꿨다.** 표시용은 아니지만 사람이 읽는
  값이고, UTC 면 한국 시간 오전 9시에 날짜가 넘어간다.
- **반응형은 '무엇을 접을 것인가' 가 설계다.** 스토어 헤더는 회원 메뉴 9개가 한 줄에
  안 들어가 글자가 세로로 쪼개졌다 — lg 미만에서 접고 **장바구니만 밖에 남겼다**(가장
  자주 누른다). 관리자 사이드바(w-60)는 좁은 화면을 거의 다 덮어서 드로어로 바꿨다.
- **표는 감추지 않고 가로로 스크롤시킨다.** 열을 숨기면 관리자가 필요한 값을 못 본다.
  열 수에 따라 최소 너비를 다르게 줬다(5열↑ 44rem, 4열 32rem, 3열 이하는 그대로) —
  일괄로 큰 값을 주면 작은 표까지 불필요하게 스크롤된다.
- **검증은 눈이 아니라 숫자로 했다.** `scrollWidth > clientWidth` 를 iframe 으로
  전 페이지에 돌려 360/375/768px 에서 넘침 0을 확인했다. 스크린샷만 보면 놓친다.

### 상품 트래킹 (조회 → 장바구니 → 구매)

- **조회수와 장바구니 담기는 그 순간에 세지 않으면 영영 알 수 없다.** 주문은
  `order_items` 에 남아서 언제든 다시 집계할 수 있지만, "상품 상세를 열었다" 는
  사실은 아무 테이블에도 흔적이 없다. 그래서 이벤트 시점에 카운터를 올린다.
- **그 결과 한 테이블에 성격이 다른 컬럼이 섞였다** — 되살릴 수 없는 누적값
  (`view_count`/`cart_count`)과 재계산 대상(`order_count`/`quantity`/`revenue`).
  **재집계가 `updateOrCreate` 로 전체 컬럼을 쓰면 조회수가 0 이 된다.** 그래서
  `ProductStatLibrary` 는 두 그룹을 건드리는 메서드를 완전히 분리했고,
  `recomputeSales()` 는 판매 컬럼만 명시해서 쓴다. 검증 항목에도 넣어뒀다.
- **카운터는 `increment()` 로 올린다.** 읽고-더하고-쓰면 동시 요청에서 값이 덮여
  사라진다. DB 가 원자적으로 더하게 맡긴다.
- **장바구니는 수량이 아니라 '담은 행위' 를 센다.** 보고 싶은 값이 "조회 대비 얼마나
  담기로 이어지는가" 이기 때문이다. 3개를 한 번에 담아도 1이다.
- **집계 트리거는 트랜잭션 밖에 뒀다.** 통계 쓰기가 실패해도 장바구니 담기는 이미
  정상 처리된 상태여야 한다 — 부가 기능이 본 절차를 막으면 안 된다(배송지 저장과 같은 원칙).
- **`ProductStatLibrary` 는 `Admin` 이 아니라 `Product` 아래에 뒀다.** 쓰는 쪽은
  스토어프론트이고 읽는 쪽만 관리자다. 이름만 보고 "관리자 전용" 으로 오해하면
  스토어프론트에서 부르는 게 이상해 보인다.
- **전환율은 조회가 0 이면 계산하지 않고 null 로 내린다.** 0으로 나눌 수 없기도 하지만,
  0/0 을 0% 로 찍으면 "이 상품은 안 팔린다" 는 정반대 결론을 유도한다. 화면은 '-' 로 그린다.
- **전체 전환율은 상품별 전환율의 평균이 아니라 합계 기준이다.** 조회 3건짜리 상품의
  100% 가 전체 평균을 끌어올리면 숫자가 거짓말을 한다.
- **매출 기준이 매출통계와 다르다.** 여기는 할인 전 상품 합계(`order_items.subtotal`)라
  쿠폰·배송비가 빠져 있다 — 매출통계의 '상품 합계' 와 같은 값이다. 화면에 그 사실을 적어뒀다.
  (검증에서 두 집계가 독립적으로 712,000원으로 일치하는 것을 확인했다.)
- **데모 데이터를 따로 만들어야 했다.** 데모 주문은 과거 날짜로 생성되는데 그때의 조회
  기록은 존재하지 않는다. 안 만들면 "판매는 있는데 조회 0" 인 앞뒤 안 맞는 화면이 된다.
  `DemoTrafficSeeder` 가 **실제 판매량에 맞춰** 조회 ≥ 장바구니 ≥ 구매 순서를 지키며 만든다.
  판매량은 `daily_product_stats` 가 아니라 `order_items` 에서 직접 센다 — 집계 커맨드가
  먼저 돌았는지에 결과가 달라지면, 시더 실행 순서에 기대는 코드가 되어 언젠가 조용히 어긋난다.

### 모바일 메뉴 재구성 · 실사 사진 · UI 참고 스킬 (2026-08-26)

**모바일 메뉴**

- '메뉴' 글자 버튼으로 2열 링크를 펼치던 방식은 기능만 했다. 국내 커머스 앱의
  통상 구조(상단 고정 바 + 왼쪽 서랍 + 하단 탭바)로 바꿨다.
- **하단 탭에 4개만 뒀다** — 홈·카테고리·장바구니·마이. 엄지가 닿는 자리라 자주 쓰는
  것만 올리고 나머지는 서랍으로 넘겼다. (스킬 데이터의 `bottom-nav-limit` 도 "최대 5개,
  아이콘에 라벨을 붙일 것" 이라 하는데 결과적으로 맞았다.)
- **아이콘 패키지를 새로 달지 않았다.** 필요한 개수가 적어서 `Icon.vue` 에 경로만 뒀다.
  24×24 stroke + `currentColor` 라 크기·색이 글자를 따라간다.
- 고정 요소가 겹치지 않게 `main`·`footer` 에 `pb-24`, 상담 버튼은 `bottom-20` 으로 띄웠다.

**데모 상품 사진을 실사로**

- **저장소에 사진을 넣어뒀다.** 시드 시점에 내려받으면 네트워크가 없거나 원본 서비스가
  바뀔 때 `shop:demo` 가 실패한다. 800×800 JPEG(품질 72)로 재압축해 3MB.
- **Unsplash 무료 라이선스만 쓴다.** 검색 결과에 `plus.unsplash.com`(Unsplash+ 유료)이
  섞여 나오는데, 내려받는 쪽에서 걸러 `images.unsplash.com` 만 통과시킨다.
  표기 의무는 없지만 촬영자를 `photos/CREDITS.json` 에 남겼다.
- **파일이 없으면 예전 GD 방식으로 물러난다**(`DemoPhotoLibrary`). 사진을 지우거나 새
  상품에 사진을 아직 안 넣어도 시딩은 끝까지 돌아야 한다.
- **원본을 그대로 업로드에 넘기지 않고 임시 파일로 복사한다.** 업로드 처리가 파일을
  옮기면 저장소의 원본이 사라져 다음 `--fresh` 부터 사진 없이 돌게 된다.

**UI/UX 참고 스킬 (3자, MIT)**

- `ui-ux-pro-max-skill` 을 붙였다. CLI 가 스킬 7개를 한꺼번에 까는데 **하나만 남기고
  지웠다** — `ui-styling` 은 shadcn/React 전제라 Vue 인 이 프로젝트에 잘못된 방향을 주고,
  로고·배너·발표자료 스킬은 안 쓴다. **스킬 설명문은 항상 컨텍스트에 올라가므로
  무관한 게 많으면 도움이 아니라 방해다.**
- **'디자인 시스템 생성기' 로 쓰지 않는다.** 이 프로젝트 조건으로 돌려보면 민트 배경 +
  에메랄드 + 오렌지에 SaaS 랜딩 구조를 제안하는데, 한국 패션몰과 거리가 멀고 한글 폰트를
  다루지 않는다. 화면 45개의 톤이 이미 잡혀 있어 새로 생성하면 갈아엎는 일이 된다.
- **검수 체크리스트로 쓴다.** 실제로 값을 했다 — 이모지를 아이콘으로 쓰던 3곳과
  `cursor-pointer` 누락, `prefers-reduced-motion` 미대응을 잡아냈다.
- 출처·라이선스·삭제한 목록은 `.claude/skills/README.md` 에.

**옵시디언 볼트**

- `docs/` 를 그대로 볼트로 쓴다. **문서를 복사해 옮기지 않았다** — 사본을 만들면 원본과
  어긋나고 어느 쪽이 맞는지 알 수 없게 된다.
- 저장소 루트를 볼트로 잡으면 `vendor`·`node_modules` 의 마크다운 407개가 딸려 들어온다.
- 홈 노트의 링크는 **손으로 적지 않고 실제 파일의 제목에서 생성**했고, 61개가 전부
  실존하는 노트·제목을 가리키는지 스크립트로 확인했다.

### Vue 컴포넌트 정리 (2026-08-26)

- **레이아웃 본체에는 조립과 열림 상태만 남겼다.** `StoreLayout` 289줄 → 58줄,
  `AdminLayout` 190줄 → 57줄. 머리·서랍·하단 탭·바닥·사이드바를 `Layouts/Partials/` 로 뺐다.
  서랍 열림 상태만 부모가 들고 있는데, **헤더와 하단 탭 양쪽에서 열 수 있어서**
  공통 부모가 아니면 둘이 각자 상태를 갖게 된다.
- **메뉴 목록은 컴포저블로 뺐다**(`useStoreNav`). 헤더(넓은 화면)·서랍·하단 탭 세 곳이
  같은 목록을 본다 — 각자 적어두면 메뉴를 하나 추가할 때 한 군데를 반드시 빠뜨린다.
- **페이지네이션이 8곳에 복사돼 있었다.** 한 곳만 고치면 나머지 7곳이 조용히 달라지는
  상태였다. `Pagination.vue` 하나로 합치고 다른 점만 prop 으로 뺐다 — 관리자/고객의
  배경색(`theme`), 상품 상세의 후기·문의처럼 화면 일부만 넘길 때의 `preserve-scroll`.
- **`link.label` 을 `v-html` 로 넣는 것은 그대로 뒀다.** `&laquo;` 같은 엔티티라
  그냥 찍으면 글자가 그대로 보인다. **서버(Laravel 페이지네이터)가 만든 문자열이라
  사용자 입력이 섞이지 않는다** — 이 전제가 깨지면 위험해지므로 주석에 적어뒀다.
- **클래스 묶음은 `ui.js` 에 이름을 붙였다.** `inputClass` 가 24곳에 흩어져 있었고
  그 사이에 `mt-1 w-full` 이 붙거나 안 붙는 미세한 차이가 섞여 있었다 — 어느 쪽이
  의도한 것인지 알 수 없는 상태였다.
- **똑같은 것만 합쳤다.** `max-w-sm` 이나 `disabled:opacity-40` 이 붙은 5곳은 그대로 뒀다.
  통일하려고 지우면 화면이 조용히 바뀐다. **중복을 없애는 것보다 화면이 안 바뀌는 게 먼저다.**
- **관리자(어두운 배경)와 고객(흰 배경)은 합치지 않았다.** 테두리·포커스 색이 반대라
  하나로 만들면 조건 분기가 클래스 안으로 들어가고 그때부터 읽기 어려워진다.
